# Clothes Selector — product quality and edge-case review

**Reviewed:** September 30, 2026  
**Source:** `Clothes_Selector-asdas (8).zip`  
**Purpose:** A decision-ready backlog for making the current app feel dependable and complete. No application code was changed.

## What I reviewed and how to read this report

I traced the recommendation generator, scoring and explanation logic, weather and preference controls, wardrobe entry/search, saved looks, wear logging, photos, account collections, migrations, and the existing tests and product documents. The archive has an Expo app with manual wardrobe entry, a deterministic outfit engine, demo and connected modes, and a partially implemented release checklist. Findings marked **Confirmed** follow directly from the source. **Needs validation** means the scenario is credible but depends on device, database, timing, or a large-closet run that I did not execute. This was a source review, not a live-device or staging-backend test. The archive's September 28 implementation-status document reports a passing suite from an earlier run; I did not rerun it in this environment.

**Priority:** P0 = potential data corruption, duplicate action, or broken core journey; P1 = frequent wrong recommendation or misleading behavior; P2 = important polish or completeness. A recommendation's numerical score is an editorial heuristic, not a validated measure of outfit quality.

## The hot and rainy example

**Confirmed:** Rain does not favor trousers over shorts. The engine requires a `bottom`, but both shorts and pants occupy the same category. Its weather score checks average recorded warmth, extreme temperatures, an outer layer, shoe/coat rain flags, and summer/winter season tags; it never checks the bottom's cut, length, coverage, or rain suitability (`src/features/recommendations/engine.ts:167–186, 337–366`). At 80°F, a light pair of shorts can score well despite rain. The probability field is stored but never read by the generator. The rain toggle sets it to exactly 1 or 0 (`src/components/styling/ContextSheet.tsx:55–65`).

The right product rule is **not** “rain always means pants.” In hot rain, quick-drying shorts can be preferable for some people; others want leg coverage or are going to work. Let the wearer specify exposure, coverage, and dress expectations. Then rank recorded properties appropriately, and explain uncertainty when a garment's performance is unknown. A sensible acceptance scenario is: at 86°F with expected rain and a stated *covered legs* requirement, every result contains a suitable full-length bottom; without that requirement, both shorts and light trousers may be offered, with rain tradeoffs clearly stated. The app should never infer that cotton, denim, or a garment name alone guarantees quick drying or rain resistance.

## Quality bar for a polished release

1. **Context and constraints.** The person can state temperature, chance/current rain, time outdoors, leg coverage, and an actual dress requirement. The app distinguishes a requirement from a preference and does not silently discard a lock. If no outfit satisfies the requirements, it names the conflict and offers a choice to revise them.
2. **Grounded garment data.** Store unknown separately from “no” for protection, warmth, season, fit, and dressiness. Add only the questions that alter a recommendation. A water-resistant flag should not imply a fully waterproof outfit; the UI should use the strength of the recorded claim.
3. **Candidate structure and ranking.** Generate useful layers and suit outerwear; apply true constraints before scoring; compare bottoms and footwear for the actual weather and stated coverage. Retain varied looks instead of repeatedly changing a minor accessory. Evaluate broad tastes and cultural/comfort needs with opt-in user input rather than universal rules.
4. **Reliable actions.** A saved look has a clear identity; recording a wear is idempotent or safely recoverable; uploaded photos have cleanup and expired-link recovery; offline and session failures state what succeeded.
5. **Evidence of quality.** Define a curated scenario set, get human ratings from varied wearers, and log only privacy-safe signals with consent. Do not market a score or a “works for rain” explanation as objectively correct before those claims are tested.

## Acceptance scenarios for the next implementation pass

| Scenario | Expected outcome |
| --- | --- |
| 86°F, rain expected, user requires covered legs; closet has shorts, light trousers, heavy jeans | Recommend suitable full-length bottoms if available; explain any unknown rain performance. |
| 86°F, rain expected, no coverage preference | Consider shorts and light trousers; do not automatically ban either. |
| 80°F versus 90°F with a 7/10-warmth coat | The choice changes coherently and visibly; no unexplained step between nearby temperatures. |
| 40°F, shorts, light shoes, warm outerwear | A warm coat does not hide exposed legs or insufficient footwear. |
| Rainy formal occasion, suit, resistant coat and shoes | Produce the coat-over-suit look or clearly explain the unsupported combination. |
| Rain required; only unknown protection fields | Do not claim protection; ask for confirmation or show a specific unmet requirement. |
| Formal occasion with unknown dressiness; black-tie explicitly required | Do not present an unverified outfit as black-tie compliant. |
| User marked red “never show”; red item is locked | Show a clear conflict and allow an explicit one-look exception. |
| Save identical garments for work and dinner | Preserve both contexts if saved looks are context-specific. |
| Wear RPC succeeds, wardrobe refresh fails, user retries | Exactly one wear event and one increment; the UI acknowledges the committed action. |
| Demo selects a photo and saves | The resulting state matches the promise made before save. |
| Storage deletion fails after garment row deletion | Object remains discoverable for cleanup, with an auditable retry. |
| Saved look loses one garment | Offer a replacement or removal path, without silently changing the original. |
| Closet has hundreds of garments and one qualifying rain set | Return the viable set within the performance target. |
| Search “pants” while owning only shorts | No false pants match. |

## Suggested order of work

**First:** Resolve S1 (duplicate wear risk), W1–W3 (rain and structure), S2 (saved-look identity), and S3 (demo photo promise). These directly affect trust in the core add → recommend → save → wear journey.

**Next:** Address W4–W10, S4–S7, and Q2–Q3 together with representative scenario tests. The weather and layering changes should be designed as one coherent model rather than patched with independent special cases.

**Then:** Improve search/filter provenance and ranking polish (F1–F4, Q1), run the documented two-account and physical-device checks, and complete the release checklist in `docs/operations/launch-readiness.md`. Record the actual backend migration state before claiming connected mode is ready; the archive's `docs/operations/implementation-status-2026-09-28.md` says the new migration and deletion function had not yet been applied to a project.

The attached design philosophy is a useful north star, but portions of its “current implementation” table describe an earlier weight vector and earlier explanation behavior (`docs/product/design-philosophy.md:134–147`). Refresh those implementation-specific passages after the next engine revision so product documentation does not contradict the shipped rules.
